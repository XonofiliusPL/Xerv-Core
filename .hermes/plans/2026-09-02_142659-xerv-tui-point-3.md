## Architecture / proposed approach (PROPOZYCJA — do zatwierdzenia)

`xerv-tui` to nowy crate binarny w workspace (`crates/xerv-tui`), który w całości korzysta z `xerv_core` przez moduł `xerv_core::api`. Technologia TUI: **ratatui** (de facto standard Rust, dobrze udokumentowany, pasywny model rysowania) + **crossterm** (backend terminala, kompatybilny z foot/kitty/itd.). Pierwsza wersja to **Event-loop z trzema panelami** (układ lazygit-style: panel boczny, panel główny, panel statusu u dołu) + **pasek górny** z metadanymi Core + **jeden ekran "Dashboard"** pokazujący podstawowe informacje z `XervCore` (wersja API, konfiguracja, stan, czy zamknięty). Nawigacja klawiaturą: `q` wyjście, `?` pomoc, `Tab`/`Shift+Tab` między panelami, `r` odświeżenie. Renderowanie odbywa się z `Terminal::new(...).draw(|f| ui(f, &app))` w pętli `App::run()`, gdzie `App` trzyma `Option<XervCore>` (lazy inicjalizacja) i `AppState`. **Żadnych** traitów rozszerzeń, rejestrów pluginów, subskrypcji — `xerv-tui` jest cienkim konsumentem `xerv-core` API. Wszystkie decyzje o layout, paleta, kursor, ramki, font/ikony Nerd Font są zaproponowane, ale wymagają zatwierdzenia.

**Granica rozszerzenia (minimalna):**
- `xerv-tui` importuje z `xerv_core::api` — to jedyna dozwolona zależność od Rdzenia.
- `xerv-tui` **nie** dodaje nowego publicznego API do `xerv-core`.
- Jeśli podczas implementacji pojawi się potrzeba nowego API w `xerv-core` (np. `XervCore::snapshot()` do pobierania stanu bez klona), **zgłaszam decyzję** zamiast samodzielnie dodawać.

## Decyzje wymagające potwierdzenia użytkownika PRZED implementacją

Każda decyzja binarna. Bez tych odpowiedzi plan nie przejdzie w implementację.

1. **Technologia TUI:**
   - (a) `ratatui` + `crossterm` (propozycja — standard Rust).
   - (b) `crossterm` + własna implementacja rysowania (minimalna, ale traci `ratatui`).
   - (c) `termion` zamiast `crossterm` (mniej popularny, podobna funkcjonalność).

2. **Zależności TUI — konkretne wersje:**
   - (a) `ratatui = "0.29"` (najnowsza stabilna) + `crossterm = "0.28"` (propozycja).
   - (b) `ratatui = "0.28"` (starsza, ale stabilna) + `crossterm = "0.27"`.
   - (c) **POWTWIERDZONE:** najnowsze stabilne kompatybilne wersje w momencie implementacji; wybór zgłoszony w wyniku.

3. **Układ ekranu (wariant):**
   - (a) **3 panele + header + footer** (lewy / główny / status), jak lazygit (propozycja).
   - (b) **2 panele + header + footer** (tylko lewy i główny), jak `rainfrog`.
   - (c) **pełnoekranowy Dashboard** bez panelu bocznego, jak `gh-dash` (z opcją bocznego panelu w przyszłym punkcie).

4. **Kolorystyka i styl:**
   - (a) ciemne tło, akcent cyan + magenta, ramki `rounded` (propozycja).
   - (b) ciemne tło, akcent zielony (jak lazygit), ramki `plain`.
   - (c) jasne tło, akcent niebieski (jak gh-dash), ramki `double`.

5. **Ikony:**
   - (a) **Nerd Font** (glyphy jak w Omarchy), z fallbackiem do ASCII (propozycja — spójne z resztą środowiska).
   - (b) **Unicode box-drawing** (bez Nerd Font), wszędzie dostępne.
   - (c) **ASCII** (maksymalnie przenośne, ale mniej estetyczne).

6. **Skróty klawiszowe (pierwsza wersja):**
   - (a) `q` quit, `?` help, `Tab`/`Shift+Tab` next/prev panel, `r` refresh, `Esc` quit fallback (propozycja).
   - (b) Vim-style: `q` quit, `h/j/k/l` nawigacja, `?` help.
   - (c) Mieszane: `q` quit, `Tab`/`Shift+Tab`, `?` help — bez nawigacji hjkl (zostawiamy na później).

7. **Inicjalizacja `XervCore` w TUI:**
   - (a) leniwa — `App::new` nie tworzy `XervCore`; tworzy przy pierwszym tyknięciu.
   - (b) **POWTWIERDZONE:** natychmiastowa — `App::try_new(...) -> Result<App>` zwraca błąd inicjalizacji; `main.rs` propaguje i wychodzi z kodem `1` + komunikat na stderr.
   - (c) osobny ekran inicjalizacji (poza zakresem Punktu 3).

8. **CLI argumenty:**
   - (a) **brak** — TUI startuje z domyślną konfiguracją (propozycja — YAGNI).
   - (b) `--config <path>` — opcjonalna ścieżka do TOML z konfiguracją `xerv-core`.
   - (c) `--config` + `--print-state` (tryb nieinteraktywny, wypisuje stan i wychodzi — to osobna binarka, raczej NIE).

9. **Obsługa błędów startu `XervCore`:**
   - (a) **TUI wychodzi** z kodem `1` i komunikatem na stderr (propozycja, jak lazygit).
   - (b) **TUI pokazuje modal** „błąd inicjalizacji, naciśnij q aby wyjść".
   - (c) **TUI startuje w trybie read-only** (bez `XervCore`, tylko pusty Dashboard).

10. **Walidacja wizualna — kolejność:**
    - (a) **po implementacji pokaż mi zrzut ekranu** (użytkownik uruchamia `cargo run` w swoim terminalu, ja dostaję opis) — propozycja.
    - (b) **zbuduj artefakt** (`cargo build --release`) i przekaż ścieżkę — użytkownik uruchamia sam.
    - (c) **zbuduj i uruchom w tle** + zrzuć `stdout` pierwszego cyklu renderowania (wymagałoby mock terminala — poza zakresem).

11. **Zależność `xerv-tui` od `xerv-core`:**
    - (a) `xerv-tui = { path = "../xerv-core" }` (workspace local, propozycja).
    - (b) `xerv-tui = { version = "0.1", path = "../xerv-core" }` (z wersją).
    - (c) publikacja na crates.io (poza zakresem).

12. **Crate `xerv-tui` — typ:**
    - (a) `[[bin]]` tylko (propozycja — YAGNI, nie potrzebujemy lib API).
    - (b) zarówno `lib` jak i `[[bin]]` (gdyby w przyszłości inny program chciał reużyć TUI).

```rust
use xerv_core::api::XervCore;

use crate::event::Event;

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Panel {
    Side,
    Main,
}

impl Panel {
    pub fn next(self) -> Self {
        match self {
            Panel::Side => Panel::Main,
            Panel::Main => Panel::Side,
        }
    }

    pub fn prev(self) -> Self {
        match self {
            Panel::Side => Panel::Main,
            Panel::Main => Panel::Side,
        }
    }
}

#[derive(Debug)]
pub enum CoreStatus {
    NotInitialized,
    Ready(XervCore),
    Shutdown,
    Error(String),
}

#[derive(Debug)]
pub struct App {
    pub core_status: CoreStatus,
    pub active_panel: Panel,
    pub should_quit: bool,
}

impl App {
    pub fn new() -> Self {
        Self {
            core_status: CoreStatus::NotInitialized,
            active_panel: Panel::Side,
            should_quit: false,
        }
    }

    /// Próba inicjalizacji XervCore. Wywoływane leniwie.
    pub fn try_init_core(&mut self, data_dir: std::path::PathBuf, state_filename: String) {
        match XervCore::new(
            xerv_core::api::CoreConfig {
                data_dir: data_dir.clone(),
                log_level: "warn".into(),
                state_filename: state_filename.clone(),
            },
            data_dir.join(state_filename),
        ) {
            Ok(core) => self.core_status = CoreStatus::Ready(core),
            Err(e) => self.core_status = CoreStatus::Error(e.to_string()),
        }
    }

    pub fn handle_event(&mut self, ev: Event) {
        match ev {
            Event::Quit => self.should_quit = true,
            Event::NextPanel => self.active_panel = self.active_panel.next(),
            Event::PrevPanel => self.active_panel = self.active_panel.prev(),
            Event::Refresh => {
                // W pierwszej wersji nic nie robi; hook na przyszłość.
            }
            Event::Tick => {
                // W pierwszej wersji nic nie robi.
            }
        }
    }
}
```

```rust
use crossterm::event::{self, Event as CtEvent, KeyCode, KeyEvent, KeyEventKind};

#[derive(Debug, Clone, Copy, PartialEq, Eq)]
pub enum Event {
    Quit,
    NextPanel,
    PrevPanel,
    Refresh,
    Tick,
}

pub fn read_event() -> std::io::Result<Event> {
    loop {
        let ev = event::read()?;
        if let CtEvent::Key(KeyEvent { code, kind, .. }) = ev {
            if kind != KeyEventKind::Press {
                continue;
            }
            return Ok(match code {
                KeyCode::Char('q') | KeyCode::Esc => Event::Quit,
                KeyCode::Char('?') => Event::Quit, // tymczasowo: brak ekranu help
                KeyCode::Tab => Event::NextPanel,
                KeyCode::BackTab => Event::PrevPanel,
                KeyCode::Char('r') => Event::Refresh,
                _ => continue,
            });
        }
    }
}
```

Stwórz `/home/xono/Projects/xerv/crates/xerv-tui/src/ui.rs`:

```rust
use ratatui::layout::{Constraint, Direction, Layout, Rect};
use ratatui::style::{Color, Modifier, Style};
use ratatui::text::{Line, Span};
use ratatui::widgets::{Block, Borders, Clear, List, ListItem, Paragraph};
use ratatui::Frame;

use crate::app::{App, CoreStatus, Panel};

const HEADER_HEIGHT: u16 = 3;
const FOOTER_HEIGHT: u16 = 1;
const SIDE_WIDTH_PERCENT: u16 = 25;

pub fn ui(f: &mut Frame, app: &App) {
    let area = f.area();
    let chunks = Layout::default()
        .direction(Direction::Vertical)
        .constraints([
            Constraint::Length(HEADER_HEIGHT),
            Constraint::Min(1),
            Constraint::Length(FOOTER_HEIGHT),
        ])
        .split(area);

    draw_header(f, chunks[0], app);
    draw_main(f, chunks[1], app);
    draw_footer(f, chunks[2], app);
}

fn draw_header(f: &mut Frame, area: Rect, app: &App) {
    let title = Line::from(vec![
        Span::styled("Xerv", Style::default().fg(Color::Cyan).add_modifier(Modifier::BOLD)),
        Span::raw("  "),
        Span::styled(format!("api {}.{}.{}", xerv_core::api::api_version().major,
                             xerv_core::api::api_version().minor,
                             xerv_core::api::api_version().patch),
                     Style::default().fg(Color::Magenta)),
    ]);
    let block = Block::default()
        .borders(Borders::BOTTOM)
        .title(" xerv-tui ")
        .title_style(Style::default().fg(Color::Cyan));
    let p = Paragraph::new(title).block(block);
    f.render_widget(p, area);
}

fn draw_main(f: &mut Frame, area: Rect, app: &App) {
    let chunks = Layout::default()
        .direction(Direction::Horizontal)
        .constraints([
            Constraint::Percentage(SIDE_WIDTH_PERCENT),
            Constraint::Min(1),
        ])
        .split(area);

    draw_side(f, chunks[0], app);
    draw_dashboard(f, chunks[1], app);
}

fn draw_side(f: &mut Frame, area: Rect, app: &App) {
    let items = vec![
        ListItem::new("Dashboard"),
        ListItem::new("(more screens soon)"),
    ];
    let block = Block::default()
        .borders(Borders::ALL)
        .title(" panels ")
        .border_style(if app.active_panel == Panel::Side {
            Style::default().fg(Color::Cyan)
        } else {
            Style::default()
        });
    let list = List::new(items)
        .block(block)
        .highlight_style(Style::default().add_modifier(Modifier::REVERSED));
    f.render_widget(list, area);
}

fn draw_dashboard(f: &mut Frame, area: Rect, app: &App) {
    let body = match &app.core_status {
        CoreStatus::NotInitialized => {
            vec![
                Line::from("Xerv TUI — first skeleton"),
                Line::from(""),
                Line::from(Span::styled("Core not initialized yet.", Style::default().fg(Color::Yellow))),
                Line::from(""),
                Line::from("Press 'q' to quit."),
            ]
        }
        CoreStatus::Ready(core) => {
            let cfg = core.config();
            let st = core.state();
            let api = core.api_version();
            vec![
                Line::from(Span::styled("Core initialized", Style::default().fg(Color::Green))),
                Line::from(""),
                Line::from(format!("  api version  : {}.{}.{}", api.major, api.minor, api.patch)),
                Line::from(format!("  data_dir     : {}", cfg.data_dir.display())),
                Line::from(format!("  state_file   : {}", cfg.state_filename)),
                Line::from(format!("  schema v     : {}", st.schema_version)),
                Line::from(format!("  boots        : {}", st.boot_count)),
                Line::from(""),
                Line::from(Span::styled("TUI działa. Wciśnij ? by zobaczyć pomoc (TODO).", Style::default().fg(Color::DarkGray))),
            ]
        }
        CoreStatus::Shutdown => {
            vec![Line::from(Span::styled("Core has shut down.", Style::default().fg(Color::Red)))]
        }
        CoreStatus::Error(e) => {
            vec![
                Line::from(Span::styled("Core init error:", Style::default().fg(Color::Red))),
                Line::from(format!("  {e}")),
            ]
        }
    };
    let block = Block::default()
        .borders(Borders::ALL)
        .title(" dashboard ")
        .border_style(if app.active_panel == Panel::Main {
            Style::default().fg(Color::Magenta)
        } else {
            Style::default()
        });
    let p = Paragraph::new(body).block(block);
    f.render_widget(p, area);
}

fn draw_footer(f: &mut Frame, area: Rect, _app: &App) {
    let keys = Line::from(vec![
        Span::raw(" "),
        Span::styled("q", Style::default().fg(Color::Cyan)),
        Span::raw(" quit  "),
        Span::styled("Tab", Style::default().fg(Color::Cyan)),
        Span::raw(" panel  "),
        Span::styled("r", Style::default().fg(Color::Cyan)),
        Span::raw(" refresh"),
    ]);
    let p = Paragraph::new(keys);
    f.render_widget(p, area);
}
```

```rust
use std::io;
use std::time::Duration;

use crossterm::event::{self as ct_event};
use crossterm::execute;
use crossterm::terminal::{
    disable_raw_mode, enable_raw_mode, EnterAlternateScreen, LeaveAlternateScreen,
};
use ratatui::backend::CrosstermBackend;
use ratatui::Terminal;

use xerv_tui::app::{App, CoreStatus, Panel};
use xerv_tui::event::read_event;
use xerv_tui::ui::ui;

fn main() -> io::Result<()> {
    // Wybierz data_dir jak w xerv_core::CoreConfig::default().
    let cfg = xerv_core::api::CoreConfig::default();

    // Terminal raw mode + alternate screen.
    enable_raw_mode()?;
    let mut stdout = io::stdout();
    execute!(stdout, EnterAlternateScreen)?;
    let backend = CrosstermBackend::new(stdout);
    let mut terminal = Terminal::new(backend)?;

    let mut app = App::new();
    app.try_init_core(cfg.data_dir.clone(), cfg.state_filename.clone());

    let result = run_app(&mut terminal, &mut app);

    // Restore.
    disable_raw_mode()?;
    execute!(terminal.backend_mut(), LeaveAlternateScreen)?;
    terminal.show_cursor()?;

    // Jeśli inicjalizacja się nie udała, wypisz na stderr.
    if let CoreStatus::Error(e) = &app.core_status {
        eprintln!("xerv-tui: core init failed: {e}");
        std::process::exit(1);
    }

    result
}

fn run_app<B: ratatui::backend::Backend>(
    terminal: &mut Terminal<B>,
    app: &mut App,
) -> io::Result<()> {
    loop {
        terminal.draw(|f| ui(f, app))?;
        // Poll z krótkim timeoutem, żeby pętla była „responsive" na resize.
        if ct_event::poll(Duration::from_millis(200))? {
            let ev = read_event()?;
            app.handle_event(ev);
        } else {
            app.handle_event(xerv_tui::event::Event::Tick);
        }
        if app.should_quit {
            return Ok(());
        }
        // Poniższa instrukcja zapobiega "unused" w zależności od wersji.
        let _ = Panel::Side;
    }
}
```

## Risks, tradeoffs, and open questions

**Ryzyka:**
- **`ratatui` 0.29 + `crossterm` 0.28** to propozycje — jeśli wersje się nie zgadzają (np. `ratatui` 0.29 wymaga `crossterm` 0.29), trzeba dostosować; bez wpływu na scope.
- **`KeyEventKind::Press`** w `event::read` — w najnowszych wersjach `crossterm` filtruje eventy; starsze wersje nie mają tego pola i wymagają innego podejścia. Jeśli kompilacja się nie powiedzie, uprościmy filtr (sprawdzenie tylko klawisza, bez `kind`).
- **`XervCore::new` zapisuje stan przy `shutdown()`** — jeśli użytkownik wyjdzie z TUI przez `q`/`Esc` **bez** wywołania `shutdown`, Rdzeń zostanie „porzucony" (ale `state.json` nie zostanie zaktualizowany — to akceptowalne dla Punktu 3, bo Rdzeń nie jest jeszcze „właścicielem" żadnego stanu). W przyszłym punkcie dodamy `Drop` albo jawny handler.
- **Brak `Drop` na `App`** — `XervCore` w `Ready` jest porzucany; `Mutex` nie trzyma żadnych zasobów systemowych, więc to nie jest wyciek, ale **każde wyjście z TUI pomija `shutdown()`** — użytkownik powinien o tym wiedzieć (komunikat w dashboardzie).
- **Layout 3-panelowy** może wyglądać dziwnie na bardzo wąskich terminalach (< 60 kolumn) — nie obsługujemy tego w Punkcie 3; `Constraint::Min(1)` dla głównego panelu minimalizuje uszkodzenie.

**Tradeoffi (świadomie wybrane, do potwierdzenia):**
- **`ratatui` + `crossterm`** zamiast pisania własnego renderera. Pro: mniej kodu, lepsza kompatybilność z terminalami. Con: zależność od zewnętrznego ekosystemu.
- **Brak myszy.** Pro: prostota, spójność z lazygit/rainfrog. Con: mniej intuicyjne dla nowych użytkowników.
- **Jeden motyw, bez konfiguracji.** Pro: zero kosztów utrzymania. Con: użytkownicy z jasnym terminalem mogą narzekać.
- **Leniwa inicjalizacja `XervCore`.** Pro: `App::new` nie może się nie powieść. Con: pierwsze `tick` po starcie może pokazać `Error`, a nie `Ready`.

**Otwarte pytania (przeniesione do sekcji „Decyzje wymagające potwierdzenia"):**
- technologia TUI, wersje, układ ekranu, kolorystyka, ikony, skróty, inicjalizacja Core, CLI argumenty, obsługa błędów startu, walidacja wizualna, zależność `xerv-tui` od `xerv-core`, typ crate (bin vs bin+lib).

**Pytania odrzucone (nie w Punkcie 3):**
- Jak wygląda integracja z modułami/pluginami/agenty? — **przyszły punkt**.
- Jak wygląda ekran modułów / ekran agentów / ekran VPS? — **przyszły punkt**.
- Jak wygląda CLI (osobna binarka)? — **przyszły punkt**.
- Jak wygląda integracja z Omarchy / foot? — **osobny temat, raczej nigdy w `xerv-tui`**.
- Jak wygląda persystencja UI między uruchomieniami? — **przyszły punkt**.

**Potencjalne API Rdzenia, które może być potrzebne w przyszłości (zgłaszam, nie implementuję):**
- `XervCore::is_shutdown() -> bool` (już istnieje, Punkt 2) — wykorzystane w `CoreStatus::Shutdown`.
- `XervCore::clone()` / `XervCore::snapshot()` — Rdzeń ma prywatne pola; konsumenci dostają pełną instancję przez `XervCore::new` lub `XervCore::state()` (klon `CoreState`). To wystarczy dla Punktu 3.
- **Gdyby** przyszły punkt chciał subskrypcji eventów z Rdzenia — to **nowa funkcjonalność Rdzenia**, nie Punkt 3.
